## 1. 结论先行：06 "标注准确"的真正原因

不是渲染器更准 —— plus01&02 用的是**同一份 9 个渲染器文件（零改动）**。差别在**驱动方式**：

| 维度 | 06（add01 viewer） | plus01&02（改造前） | 后果 |
|---|---|---|---|
| 画布 | **每个 layer 一张** `.canvas-card` + `<canvas>` | 一张 canvas，所有层叠着画 | add01 的每个渲染器都把**整块 rect 当自己的画布**（`name` 在 `rect.x+16`、`fitRow` 的 `y0 = rect.y+40`）→ 多层必然互相压。实测 **632/972 步是多层，最多 3 层，涉及 35/54 案例** |
| 画布尺寸 | `cv.width = max(320, rect.width*dpr)`、`cv.height = max(180, rect.height*dpr)`；CSS `height:300px` | 一张 canvas 塞进 560px 窗口（可用高 ~380px） | `fitRow` 的 `cellH = clamp(46, rect.h*0.44, 78)`，高度越小越挤；固定 14/34px 偏移更显拥挤 |
| 绘制入口 | `drawTween(ctx, rect, from, to, t, {bg})`（`t>=1` 即静态整帧） | 自己写 `layout()` + `paint2D()` 循环 | 少了 from→to 的补间能力，也容易漏掉 clear 细节 |
| 画法开关 | 按 style 给 6/4/2/2/2 组 props（`shape/showGrid/showLine/drawMode/roundShape/layout`）并合并进每层 | 没传（走渲染器默认值） | 06 的"矩形/点/网格/连线/曲面/树后端/图布局"全都没生效 |

> 附：`one-array` 自身有两处固定偏移 —— 指针气泡在 `cell.y - 14`、区间标签 y 恒等于 `axisY`（画在 X 轴线上）。这两处在 06 里也一样，只是每层独立大画布 + 300px 卡高时视觉不冲突。

## 5. 画布内还剩的两处压叠：`polishLayout` 为什么不改渲染器

分卡之后仍有两处压叠，**都在 `one-array` 渲染器内部，是固定偏移造成的**，06 也有：

| 现象 | 成因（`vendor/engine/renderers/one-array.js`） | 为什么不在渲染器里改 |
|---|---|---|
| `hi=1` 气泡压在虚线区间框上 | 指针气泡 `chip.y = cell.y - 14`，区间框 `range.y = cell.y - 34`、`h = cell.h + 34` → 气泡与框的上沿重叠 | 该文件是 add01 **零改动 vendor 副本**，改了就失去"与 06 同一份渲染器"的可比性 |
| `[1,1]` 区间标签压在 X 轴刻度上 | `range-label.y = axisY` 恒定？→ 直接落在 X 轴线上，与 `axis-x` 的刻度数字重叠 | 同上 |

做法：在 `app/canvas-stage.js` 里加一层**后处理 `polishLayout(prims, rect)`**，只动图元坐标、不碰语义、不碰 vendor：

1. **区间框贴格**：`range.y = cell.y`、`range.h = cell.h`（框只圈住格子本身，不再向上吞气泡）；
2. **区间标签下移**：`range-label.y = cell.y + cell.h + 34 + 32`，即"格底 → 跳过下标数字 → 再跳 32px"，落到下标与 X 轴之间的空白带；
3. **同格气泡成簇摊开**：把落在同一 `cell` 上的指针 chip 归簇，间距按簇内最宽气泡自适应（`gap = max(46, maxW + 10)`），`x` 左右对称摊开、`y` 交替 `-22px` 抬起，同时重锚连接线 `line.x1 = chip.x`、`line.y1 = chip.y + chipH/2 + 2`（线从格子顶斜指到气泡，仍然一一对应）。

## 7. 树的排布（style 9 / TTreeForm）——你截图里那棵树的两个真问题

你截图里 `平衡二叉树` 那棵树"看着不对"，不是标注问题，是 `vendor/engine/renderers/tree.js › layoutAsCanvas` 的**排布缺陷**（06 同样有，因为代码一样）：

| # | 缺陷 | 根因（tree.js） | 实测规模 |
|---|---|---|---|
| ① | **多个结点完全叠在一点** | `assign()` 只从 `data.roots` 出发；`collect()` 兜底把不可达结点放进 `order`（depth 0），但它们**从没被 assign**，`px()` 里 `xs.get(id) ?? 0` 一律取 0 → 都画在 `(500, 62)` | **33 层**（B 树的"提升键"、最优归并树、树/森林转换） |
| ② | **单孩子链塌成一条竖线** | `assign()` 取孩子中点；只有一个孩子时"中点＝孩子本身" → 整棵树退化成竖直链，左右看不出 | **70 层**（AVL、红黑树、二叉树重建、树/森林转换） |

修法：`app/canvas-stage.js › polishTreeCanvas()`（**只改坐标，渲染器文件仍与 add01 逐字节相同**）

1. 不可达结点也当作根参与 tidy 排布（B 树那三个结点变成横排）；
2. 单孩子时父结点朝孩子的**反侧**偏 0.6 格（AVL 的 3→2→1 变成左下台阶，能看出左左链）；
3. 同深度最小间距 `r1 + r2 + 18` 兜底，整组水平居中；
4. `levelGap` 从 `(h-70)/(depth+1)` 改为 `(h-110)/depth`（上限 110）——原来"父的 `h=xx` 文字"和"孩子的 `bf=` 气泡"之间只剩 0.7px，标签根本没有落点；
5. `badge` / 边标签 `L`·`R` / 指针气泡三者**互相让位跑两轮**（各自只避让别人当前位置，一轮会互相追尾；第二轮 badge 就回到正上方）；
6. 指针气泡改成"绕结点找空位 + 箭头指入"（原来固定 `(cx+34, cy-26)` + 一小段斜线，紧凑排布里会悬空、盖住别的结点）。

## 9. 链表（style 3 / TLinkForm）的"错位"：气泡被推进了结点框

你截图里 `单链表逆置` 的 `prev` / `cur` / `next` 错位，是我上一轮自己引入的：

| 项 | 说明 |
|---|---|
| 现象 | `next` 比 `cur` 高 22px、压进结点 3 的框里，虚线从框内起画；`prev` 也贴着框底 |
| 真因 | `polishArrayLayout` 里"同格气泡成簇摊开"的纵向错开**只朝上**（`-22`）。这条规则本来是给一维数组写的——数组气泡在**格子上面**，往上错开是"离开格子"；而 `link-2d.js` 的指针气泡在**结点框下面**（`py = g.y + g.h + 16`），往上错开正好是"推进框里" |
| 修法 | 由配套虚线的走向判定上下：`ln.y2 >= ln.y1` = 气泡在目标上方（往上错开、线锚气泡底边）；否则气泡在下方（往下错开、线锚气泡顶边）。并且**只在横向摊开后仍然挨着时才换行**，摊得开就排一行 |

实测（`e/singly-linked-list-reverse`，685px 宽画布）：`prev/cur/next` 全部在 `y=169`（框底 153 下方 5.5px）排成一行，虚线各自从气泡顶边 3~5px 引到框底；`cur`/`next` 同时指向 n3 时并排落在该框正下方。

> 审计工具补了两件事：
> ① `overlap-audit.mjs` 现在也检查"指针气泡 × **结点框/格子框**"（之前只查气泡×气泡、气泡×区间框，所以这类"推进框里"没被抓住）；
> ② 新增 `--rect 685x300` 参数，可以按真实窗口里的卡片宽度复核（1000 / 800 / 685 宽：重叠 187→0、出界 0→0；560 宽出现的 34 步出界是渲染器自身在极窄画布下的老问题，修前修后一样多）。

## 11. 去掉硬编码：排版改成"角色驱动"（为"任意 结构 × 算法"做准备）

**问题**：`polishLayout` 虽然只是后处理，但把**图元键名**和**偏移量**写死在代码里（`nv-` / `nb-` / `cell-` / `range-label` / `dot-`…、`-16` / `22` / `46` / `70` / `0.6 格`）。那样只有这 9 个渲染器能吃到排版：将来接入新的"数据结构 × 算法"组合，渲染器换了命名，polish 立刻失效，只能回来改代码。

**改法**：把"约定"和"数字"从逻辑里抽出来，代码里不再出现键名与魔数。

| 文件 | 行数 | 职责 | 里面允许出现键名/数字吗 |
|---|---|---|---|

## 12. 卡片高度跟着内容走 + 栈/堆的 pass 顺序（截图里那两张 style 8 卡）

你截的那屏是 `置换选择`：`内存工作区 WA`（2 格）和 `输入流 FI`（5 格）——**两张卡都是 style 8**，是因为"画法"下拉把每层都换算成了 THeapForm（`adaptStepLayers`）。查出来的两个问题：

| 现象 | 根因 | 修法 |
|---|---|---|
| 两张卡内容基线不齐：`WA` 的格子在 y=53、`FI` 在 y=40 | `WA` 的标题很长，`新读入 5` 气泡落在标题的 x 区间内 → `header` pass 把整组内容下移 13px；`FI` 标题短、气泡在标题右侧外，所以没触发 | style 7/8 的 pass 顺序改成 `float → header → float`：**先让气泡自己找位置**（塞格子右侧/下方都行），就不再需要整体下移 |
| 卡片下方一大片空白（2 个格子占满 300px） | 卡片高度写死 300（与 06 一致），不管内容多少 | `createStage.render()` 改成**高度跟内容**：先画一帧量内容下边界，差 >12px 就改卡高重画一次（装不下退回 300）；下限 130、上限 300 |

改完后（586 宽，截图同款）：

```
layer wa (style 8)      cells y 40..70      chip 新读入 5 @176,40   （在格子右侧，不压标题）
layer stream (style 8)  cells y 40..65      chip 读指针 3 @204,26   （在格子上方）
两张卡基线一致；WA 卡高按内容收缩，FI 卡按内容伸缩
```

新测试 `tools/card-height-test.mjs`（6 通过 / 0 失败）断言：内容少 → 卡高 < 300 且装得下；内容多 → 卡高在 [130,300] 且装得下；同一张卡换到内容更多的步 → 能自动长回来。

> 顺手给 `tools/prim-dump.mjs` 加了 `--style N`：复现"画法换算后"的图元（截图现场就是换算过的），排查这类问题不用再写临时脚本。
